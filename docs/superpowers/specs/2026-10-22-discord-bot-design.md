# تصميم بوت ديسكورد شامل لسيرفر واحد

- التاريخ: 2026-10-22
- الحالة: مسودة بانتظار الموافقة
- المسار المختار: بناء نظيف من الصفر
- اسم العمل المؤقت: Nizam Bot

## 1. الهدف والسبب

نريد بوتًا واحدًا يدير سيرفر ديسكورد واحدًا بالكامل، بدل تشغيل عدة بوتات لكل وظيفة. البوت يجب أن يجمع الحماية والإدارة واللوقات والمجتمع والاقتصاد والتذاكر والموسيقى والأدوات، بواجهة عربية أولًا، وبدون أي إيموجي في المحتوى الذي يكتبه البوت.

السبب العملي:

- ملكية كاملة للبيانات محليًا.
- سلوك موحّد وصلاحيات موحّدة بدل تعارض عدة بوتات.
- إمكانية تعديل أي شيء دون انتظار بوت مدفوع.
- حماية مبنية على نموذج تهديد واضح، لا مجرد أوامر إشراف.

معايير النجاح:

- عملية واحدة تعمل على Windows وتُشغّل كل الوحدات الأساسية.
- كل أمر في مصفوفة الأوامر يعمل بالعربية دون إيموجي.
- سيناريوهات الاختبار الأمني (سبام، ريد، نيوكن) تُحتوى وتُسجّل.
- دورة تذكرة كاملة تعمل مع نسخة محفوظة آمنة.
- اختبارات وفحص أنواع وفحص إيموجي تمر قبل كل تسليم.
- استعادة نسخة احتياطية مُجرّبة فعليًا.

ملاحظة صريحة: لا يمكن ضمان "صفر عيوب" برمجيًا. ما يمكن ضمانه هو بوابات جودة صارمة، اختبارات، نسخ احتياطي، مفاتيح إيقاف، ونشر تدريجي. هذا التصميم مبني على هذا المبدأ.

## 2. النطاق

### 2.1 داخل النطاق

- سيرفر واحد محدد عبر `GUILD_ID`.
- أوامر سلاش فقط، مع قوائم سياقية محدودة. لا أوامر بادئة نصية.
- وحدات: الأساس، الأمان، الإشراف، اللوقات، المجتمع، المستويات، الاقتصاد، التذاكر، الموسيقى، الأدوات، الألعاب، لوحة التحكم.
- واجهة عربية مع احتياطي إنجليزي، وبنية i18n قابلة للتوسعة.
- منع الإيموجي في كل نص يكتبه البوت، مع فحص آلي.
- قاعدة بيانات محلية SQLite، نسخ احتياطي واستعادة.
- لوحة تحكم ويب محلية ضمن النطاق الكامل في المرحلة 5. كونها "اختيارية" يعني أنها قابلة للتعطيل أو التأجيل، لا حذفها من النطاق النهائي.
- نشر على Windows، مع توافق Linux وDocker.
- اختبارات وحدات وتكامل، وفحص أمني، واختبار تحميل خفيف.

### 2.2 خارج النطاق

- بوت عام لسيرفرات متعددة، Sharding، نظام اشتراكات أو Premium.
- استضافة سحابية مُدارة أو خدمة SaaS.
- تطبيق جوال أو واجهة خارج المتصفح.
- ضمان عدم وجود أخطاء أو ثغرات مطلقًا.
- محتوى NSFW.
- Self-bot أو أتمتة حساب مستخدم.
- تخزين تاريخ الرسائل بالكامل إلى الأبد.
- بيع العملات الافتراضية أو ربطها بمال حقيقي.
- تشغيل موسيقى عبر تنزيل الملفات أو كسر قيود المنصات.

### 2.3 أهداف مضادة

- نسخ TitanBot أو أي بوت جاهز كما هو: نرث عيوبه ونفقده السيطرة.
- تقسيم البوت إلى Microservices: تعقيد بلا فائدة لسيرفر واحد.
- الاعتماد على API مدفوع أو خدمة خارجية لوظيفة أساسية.
- استخدام إيموجي أو رموز تعبيرية في واجهة البوت.
- طلب صلاحية Administrator للبوت بدل الصلاحيات الدقيقة.
- بناء لوحة تحكم قبل تثبيت النواة والأمان.

## 3. القيود والافتراضات

| البند | القرار |
|---|---|
| السيرفر | سيرفر واحد، `GUILD_ID` إلزامي |
| نظام التشغيل | Windows 11 حاليًا، مع توافق Linux |
| العتاد | حوالي 8 GB RAM، لا يحتاج خدمات ثقيلة |
| وقت التشغيل | Node.js 22 LTS |
| اللغة | TypeScript 5 بإعداد strict |
| مكتبة ديسكورد | discord.js 14.27 |
| قاعدة البيانات | SQLite بوضع WAL عبر better-sqlite3 وDrizzle ORM |
| الذاكرة المؤقتة | LRU داخل العملية، لا Redis |
| الموسيقى | Lavalink 4 اختياري، يتطلب Java 17 |
| لوحة التحكم | Fastify وEJS وhtmx، محلية افتراضيًا |
| النشر | عملية واحدة + Lavalink اختياري |
| الترخيص المقترح | MIT للكود الأصلي، مع احترام تراخيص المكتبات |
| التوثيق | عربي أساسًا، مع مصطلحات تقنية إنجليزية |

افتراضات قابلة للتصحيح:

- الواجهة عربية أولًا مع إنجليزي احتياطي، وليس العكس.
- المستخدم هو مالك السيرفر وسيوفر التوكن و`GUILD_ID` و`OWNER_ID`.
- لا توجد حاجة لاستضافة عامة أو نطاق إنترنت في المرحلة الأولى.
- الموسيقى مطلوبة وظيفيًا، لكنها تبقى اختيارية تشغيليًا حتى تجهيز Lavalink.
- لوحة التحكم مطلوبة ضمن "كل شيء"، لكنها آخر المراحل، ومحلية فقط في المرحلة 5.
- وحدة الذكاء الاصطناعي اختيارية ومطفأة افتراضيًا، ولا تعطّل أي وظيفة أساسية.
- لا توجد بيانات قديمة تُرحّل: نبدأ قاعدة بيانات نظيفة. أي ترحيل لاحق مشروع مستقل.
- الوصول البعيد للوحة مؤجل إلى مرحلة لاحقة بعد المرحلة 5، ويحتاج نفقًا آمنًا وTLS.
- الترجمة والطقس والذكاء الاصطناعي وحدات اختيارية مطفأة، تعمل فقط عند إضافة مفتاح، ولا تدخل بوابة القبول الأساسية.

## 4. المسارات التي وُزنت

### المسار الأول: استنساخ TitanBot وتخصيصه

- المزايا: 129 أمرًا، لوحة ويب، PostgreSQL، MIT، وصول سريع لبوت شامل.
- العيوب: بلاغات مفتوحة عن تعطل الموسيقى والمستويات والتذاكر، وطلب إصلاح ثغرة حقن في الاقتصاد لم يُدمج، وواجهة إنجليزية مليئة بالإيموجي. إزالة الإيموجي والتعريب والتأمين ستلامس معظم الملفات.
- القرار: مرفوض كأساس. يُستفاد منه كمرجع أفكار فقط.

### المسار الثاني: بناء نظيف من الصفر

- المزايا: تحكم كامل في المعمارية والأمان والواجهة، عربي من البداية، منع الإيموجي على مستوى النواة، اختبارات حقيقية، لا ديون تقنية موروثة.
- العيوب: الجهد الأكبر، ويلزمه تثبيت Node وGit من الصفر.
- القرار: مختار.

### المسار الثالث: قاعدة هجينة

- المزايا: أسرع من البناء النظيف، وأكثر نضجًا من TitanBot.
- العيوب: نرث معمارية وقاعدة بيانات ورخصًا وقيودًا. `FireDiscordBot` تحت AGPL، و`saiteja-madha` تحت MIT لكنه متوقف نسبيًا ويعتمد MongoDB. التعريب ومنع الإيموجي سيصطدمان ببنية قائمة.
- القرار: مرفوض كأساس. تُؤخذ أنماط محددة فقط.

المشاريع المرجعية التي ستُدرس أنماطها دون نسخ كود غير متوافق:

- `discord-tickets/bot`: دورة حياة التذكرة والنسخ المحفوظة. الرخصة GPL-3.0، لذلك لا يُنسخ الكود.
- `appujet/lavamusic`: تجربة أوامر الموسيقى وLavalink. يُستخدم بدلًا منها `lavalink-client` المرخّص MIT.
- `Discord-Dashboard/Core`: أفكار تنظيم لوحة التحكم. الرخصة MIT.
- `YAGPDB`: أنماط Anti-Nuke وAutomod وCustom Commands. الرخصة MIT، لكن الكود بلغة Go.
- `Red-DiscordBot`: فصل الوحدات والإعدادات والترجمة. الرخصة GPL-3.0، أفكار فقط.
- `TitanBot`: قائمة الميزات وتجربة المستخدم. الرخصة MIT، ولا يُنسخ كوده.

## 5. المعمارية

### 5.1 النمط العام

Monolith معياري (Modular Monolith) في عملية Node واحدة:

```text
Discord Gateway
      |
      v
Client + Event Router
      |
      v
Interaction Router -> Guards -> Command -> Service -> Repository -> SQLite
      |                              |
      |                              +-> Scheduler (jobs)
      |                              +-> UI Kit (embeds/components)
      |                              +-> Audit Log
      v
Error Boundary -> Logger -> ملفات + Webhook اختياري

Dashboard (Fastify, مرحلة 5) -> Service Layer -> SQLite
Lavalink (Java, اختياري) <-> Music Service
```

قواعد المعمارية:

- الأوامر والأحداث لا تلمس قاعدة البيانات مباشرة. كل شيء عبر Services.
- كل خدمة قابلة للاختبار بحقن التبعيات.
- كل نص يظهر للمستخدم يأتي من i18n، لا نصوص مكتوبة داخل الأوامر.
- كل عملية حساسة تُسجّل في سجل تدقيق.
- كل وحدة قابلة للتعطيل من الإعدادات، عدا نواة الأمان الأساسية.
- لا `eval` ولا تنفيذ كود ديناميكي.

### 5.3 نواة الأوامر

كل أمر يُعرّف كائنًا واحدًا:

```ts
defineCommand({
  data: new SlashCommandBuilder()...,
  meta: {
    module: 'moderation',
    permissions: ['ModerateMembers'],
    botPermissions: ['ModerateMembers'],
    ownerOnly: false,
    guildOnly: true,
    cooldownMs: 3000,
    defer: 'ephemeral',
  },
  execute,
});
```

سلسلة الحراس بالترتيب:

1. التأكد أن التفاعل داخل السيرفر المحدد.
2. التأكد أن الوحدة مفعّلة.
3. فحص صلاحيات المستخدم.
4. فحص صلاحيات البوت في القناة.
5. فحص تسلسل الرتب للعضو الهدف.
6. فحص مدة الانتظار (cooldown).
7. التحقق من المدخلات عبر Zod.
8. التنفيذ داخل Error Boundary.

قواعد إضافية:

- تأجيل الرد خلال أقل من ثانيتين لكل أمر قد يتجاوز 3 ثوانٍ.
- معالجة `10062 Unknown interaction` و`40060 already acknowledged` بهدوء.
- بناء المكونات عبر UI Kit يفرض حدود ديسكورد: 5 صفوف، 5 أزرار لكل صف، 25 خيارًا للقائمة، 80 حرفًا للتسمية، 100 حرف لـ customId.
- كل نص Embed يمر عبر دالة تقص آمن يمنع تجاوز 256/4096/1024/6000.
- `allowedMentions` مقيّد افتراضيًا.

### 5.4 الأحداث

- تسجيل تلقائي من `src/modules/**/events`.
- كل معالج معزول: فشل حدث لا يوقف الآخرين.
- Partials المطلوبة: `Channel` و`GuildMember` و`Message` و`Reaction` و`User`.
- Intents: `Guilds`, `GuildMembers`, `GuildModeration`, `GuildMessages`, `MessageContent`, `GuildVoiceStates`, `GuildInvites`, `GuildMessageReactions`, `GuildEmojisAndStickers`, `DirectMessages`.
- `GuildMembers` و`MessageContent` مميزان ويجب تفعيلهما في بوابة المطورين. `/doctor` يتحقق منهما.
- لا نطلب Presence إطلاقًا.

### 5.5 الإعدادات

- جدول `guild_settings` بأعمدة JSON مصنّفة، مع تحقق Zod عند القراءة والكتابة.
- كاش LRU في الذاكرة، يُبطل عند أي كتابة.
- كل تغيير يمر عبر `SettingsService` ويسجّل في سجل التدقيق.
- إصدار إعدادات (`version`) لمنع الكتابة المتعارضة من اللوحة.
- `/settings` معالج تفاعلي، و`/config export` و`/config import` للنسخ.

### 5.6 المجدول

- جدول `jobs` في SQLite.
- دورة كل 5 ثوانٍ، مع `run_at` و`status` و`locked_until`.
- استحواذ ذري عبر `UPDATE ... RETURNING` لدعم عملية واحدة وإعادة التشغيل.
- أنواع المهام: إنهاء سحب، تذكير، انتهاء عقوبة مؤقتة، تحديث عدادات، نسخ احتياطي، تنظيف بيانات.
- كل مهمة Idempotent، ومفتاح فريد يمنع التكرار.
- مهام فاشلة تُعاد بمهلة أسية، ثم تُعلّم كفاشلة نهائيًا بعد 5 محاولات.

### 5.7 معالجة الأخطاء

- Error Boundary مركزي يعطي المستخدم رسالة مختصرة مع معرّف خطأ.
- السجل يحتوي: الأمر، المستخدم، السيرفر، القناة، مدة التنفيذ، معرّف التفاعل، stack مخفي عن المستخدم.
- `unhandledRejection` و`uncaughtException` يُسجّلان ثم إغلاق آمن.
- إغلاق آمن عند SIGINT/SIGTERM: إيقاف المجدول، إغلاق العميل، إغلاق قاعدة البيانات.
- ويب هوك أخطاء اختياري، مع تقييد المعدل وتنقية الأسرار.

## 6. التقنيات

| المجال | الاختيار | السبب |
|---|---|---|
| Runtime | Node.js 22 LTS | دعم طويل، توافق مع discord.js |
| اللغة | TypeScript 5 strict | أمان أنواع وتقليل أخطاء وقت التشغيل |
| Discord | discord.js 14.27 | أحدث إصدار مستقر، دعم كامل للتفاعلات |
| قاعدة البيانات | SQLite + WAL | كافية لسيرفر واحد، بلا خدمة خارجية |
| ORM | Drizzle ORM + drizzle-kit | Typed schema، ترحيلات واضحة، SQL شفاف |
| التحقق | Zod 4 | تحقق موحد للإعدادات والمدخلات |
| السجلات | Pino + دوران يومي | سريع، منظم، سهل التنقية |
| الاختبارات | Vitest | سريع، يدعم TypeScript أصلًا |
| الجودة | ESLint + Prettier + tsc | بوابات ثابتة |
| الصور | @napi-rs/canvas | بطاقات رتب، مع اختبار تشكيل العربية |
| الموسيقى | Lavalink 4 + lavalink-client | استقرار وعزل عملية الصوت |
| الويب | Fastify 5 + EJS + htmx | خفيف، بلا خطوة بناء معقدة |
| الجلسات | SQLite session store | لا Redis |
| النشر | npm scripts + PM2/NSSM اختياري | بسيط على Windows وLinux |
| الحاويات | Dockerfile + compose اختياري | نشر Linux وLavalink |
| CI | GitHub Actions | فحص تلقائي على Windows وUbuntu |

لماذا SQLite وليس PostgreSQL:

- سيرفر واحد، عملية واحدة، بيانات صغيرة إلى متوسطة.
- WAL يكفي لقراءات متزامنة وكتابات قصيرة.
- نسخ احتياطي بملف واحد، واستعادة سهلة.
- يقلل متطلبات التثبيت على جهاز لا يحتوي Docker.
- إن احتجنا PostgreSQL لاحقًا، فصل المستودعات يسهّل الترحيل.

لماذا لا Redis:

- لا حاجة لكاش موزع أو قوائم انتظار خارجية لعملية واحدة.
- LRU داخلي + جدول مهام في SQLite يغطيان الحاجة.
- تقليل الأجزاء المتحركة يقلل الأعطال.

## 7. نموذج البيانات

كل الجداول المتعلقة بالسيرفر تحتوي `guild_id` حتى مع سيرفر واحد، لتسهيل النقل أو التوسعة لاحقًا. المعرّفات النصية (Snowflakes) تُخزّن `TEXT`. الأوقات تُخزّن `INTEGER` بالمللي ثانية. JSON يُخزّن `TEXT` مع تحقق Zod.

### 7.8 حذف بيانات المستخدم

`/data delete` لا يحذف سجل الاقتصاد ولا سجل التدقيق ولا الحالات الإدارية، لأنها سجلات مالية وإدارية. بدلًا من ذلك:

- حذف أو إخفاء هوية البيانات المجتمعية: XP، الحساب الاقتصادي، المخزون، أعياد الميلاد، Tags، الاقتراحات، الدعوات.
- استبدال معرّف المستخدم في الحالات والملاحظات وسجل الاقتصاد بمعرّف مستعار غير قابل للربط، مع الاحتفاظ بالمبالغ والتواريخ.
- حذف نسخ التذاكر ورسائل Modmail التي يخصّه، ما لم تكن مطلوبة لسجل إداري.
- النسخ الاحتياطية القديمة لا تُعدّل بأثر رجعي، وتُنقى دوريًا وفق مدة الاحتفاظ.
- يُوثّق ذلك في `/data` وفي سياسة الخصوصية، مع تأكيد صريح قبل التنفيذ.

### 7.9 البيانات الأولية: نبدأ نظيف

قرار المستخدم: لا يوجد ترحيل بيانات من بوتات سابقة. تبدأ قاعدة البيانات فارغة، ولا تُبنى أدوات استيراد في النطاق الحالي.

عند أول تشغيل:

- إنشاء صف `guild_settings` افتراضي.
- ربط رتب الموظفين وقنوات اللوقات عبر `/settings`.
- عدم افتراض أي بيانات أعضاء أو أرصدة سابقة.
- توثيق ما يفقده الأعضاء عند الانتقال (مستويات وأرصدة قديمة) بوضوح قبل التشغيل.

إن ظهرت حاجة للترحيل لاحقًا، تُعامل كمشروع مستقل بمخطط تحويل وDry Run ونسخة احتياطية وخطة تراجع.

### 8.2 Anti-Nuke

الأحداث المراقبة:

- حذف قناة أو رتبة.
- حظر أو طرد جماعي.
- إنشاء ويب هوك أو بوت.
- حذف إيموجي أو ستيكر.
- تعديل إعدادات السيرفر الحساسة.

الآلية:

- قراءة Audit Log بعد الحدث مع إعادة محاولة قصيرة لمعالجة التأخر.
- تجميع الأحداث في نافذة زمنية (مثل 10 ثوانٍ أو 60 ثانية).
- استبعاد المالك، البوت نفسه، وقائمة بيضاء من المستخدمين والبوتات.
- عند تجاوز العتبة: تنبيه فوري، تسجيل، ثم إجراء قابل للضبط: سحب الرتب، طرد، حظر، أو قفل السيرفر.
- وضع تجريبي (Dry Run) افتراضي لأول 24 ساعة بعد التفعيل.
- لقطة (Snapshot) لبيانات القنوات والرتب المهمة تسمح بإعادة إنشاء ما أمكن، مع توضيح أن المحتوى المحذوف لا يُستعاد.

### 8.3 Anti-Raid

- مراقبة معدل الانضمام في نافذة قصيرة.
- فحص عمر الحساب، الصورة الافتراضية، ونمط الاسم عند الحاجة.
- رتبة حجر صحي بلا صلاحيات.
- بوابة تحقق: زر ثم Modal بسؤال رياضي أو صورة تحقق.
- وضع ريد: تعطيل الدعوات مؤقتًا، قفل القنوات العامة، تنبيه المالك، وإيقاف تلقائي بعد مدة أو يدويًا.
- تكامل مع Rules Screening في ديسكورد كطبقة إضافية.

### 8.4 Automod

القواعد:

- سبام: عدد رسائل في نافذة، تكرار محتوى، ذكر جماعي.
- روابط: قائمة سماح للنطاقات، منع دعوات ديسكورد.
- أحرف كبيرة: نسبة تجاوز حدًا مع حد أدنى لطول الرسالة.
- كلمات ممنوعة: قوائم عربية وإنجليزية قابلة للتعديل، بحدود كلمات لتقليل الإيجابيات الكاذبة.
- زالغو وتكرار أسطر ومرفقات.
- تصعيد بالنقاط: تحذير، كتم، طرد.
- استبعادات: رتب، قنوات، مستخدمون.
- كل قاعدة قابلة للتعطيل، ولها إجراء مستقل.

### 8.5 الإشراف

- حظر، حظر مؤقت، رفع حظر، طرد، كتم مؤقت، إنذار، ملاحظة، مسح رسائل، قفل قناة، بطء، تغيير كنية.
- سجل حالات مرقّم مع سبب ومدة ومشرف.
- فحص تسلسل الرتب وحماية المالك والبوت.
- تأكيد بالأزرار للعمليات الجماعية والخطيرة.
- لا حظر جماعي دون تأكيد صريح ومراجعة قائمة.

### 8.6 اللوقات

- أحداث الأعضاء، الرسائل، القنوات، الرتب، الصوت، الدعوات، السيرفر، الإيموجي، الستيكر، وإجراءات الإشراف.
- قناة افتراضية لكل نوع، مع استبعادات.
- بيانات وصفية افتراضيًا، ومحتوى الرسائل اختياري ومحكوم بمدة احتفاظ.
- تقصير آمن للـ Embed، وتجميع الأحداث المتكررة.
- تنقية أي توكن أو رابط حساس قبل التسجيل.

### 8.7 لوحة التحكم

- OAuth2 بديسكورد، نطاقات `identify` و`guilds`.
- التحقق من ملكية السيرفر أو صلاحية `ManageGuild`.
- جلسة في SQLite، كوكي HttpOnly وSameSite، CSRF، Helmet، حد معدل.
- ربط بـ `127.0.0.1` افتراضيًا.
- الوصول البعيد خارج نطاق المرحلة 5. عند الحاجة لاحقًا: نفق آمن أو Reverse Proxy مع TLS، وتقييد IP، وجلسات أقصر.
- RBAC: مالك، مشرف، موظف قراءة.
- كل تعديل يمر بنفس خدمات البوت والتحقق نفسه، ويسجّل في التدقيق.
- لا يظهر التوكن في أي صفحة أو سجل.

## 9. تجربة المستخدم والنصوص

### 9.1 اللغة

- العربية افتراضيًا، الإنجليزية احتياطيًا.
- كل النصوص في `ar.json` و`en.json`، بمفاتيح متطابقة.
- فحص آلي يتأكد من تطابق المفاتيح وعدم وجود مفاتيح ناقصة.
- أسماء الأوامر بالإنجليزية (اصطلاح ديسكورد)، والأوصاف والردود بالعربية.
- دعم RTL في اللوحة، وضبط اتجاه النص في البطاقات.

### 9.2 منع الإيموجي

القاعدة:

- لا إيموجي ولا رموز تعبيرية ولا إيموجي مخصص في أي نص يكتبه البوت: أوامر، أوصاف، Embed، أزرار، قوائم، Modals، سجلات، لوحة، توثيق.
- محتوى المستخدم (الأسماء، الرسائل، النسخ، الاقتراحات، Tags) يُعرض كما هو مع تهريب آمن. البوت لا يضيف إيموجي.
- الأيقونات في واجهة ديسكورد نفسها ليست محتوى البوت ولا تُحسب.

التنفيذ:

- `tests/i18n-no-emoji.test.ts` يفحص كل قيم i18n وبيانات الأوامر.
- `scripts/emoji-guard.ts` يفحص ملفات i18n وبيانات الأوامر والقوالب.
- دالة `assertNoEmoji` تعمل في بيئة التطوير والاختبار على أي نص يمر عبر UI Kit.
- تعبير الفحص: `\p{Extended_Pictographic}` مع الإشارات الإقليمية ومفاتيح الترميز.
- لا تُستخدم رموز مثل علامات الصح والخطأ؛ تُستبدل بكلمات عربية واضحة.

### 9.3 النظام البصري

- ألوان: خلفية داكنة محايدة، لون أساسي هادئ، أحمر للخطر، أخضر للنجاح، برتقالي للتحذير.
- Embed: عنوان، وصف، حقول مرتبة، فوتر موحد، وقت نسبي.
- أزرار: تسميات نصية واضحة، بلا إيموجي، ألوان حسب الخطورة.
- أخطاء: ماذا حدث، ماذا يفعل المستخدم، معرّف خطأ للدعم.
- لا اعتماد على اللون وحده لنقل المعنى.
- حدود ديسكورد تُفرض مركزيًا لمنع أخطاء API.

### 9.4 مصفوفة الصلاحيات

| الفئة | الصلاحيات |
|---|---|
| مالك البوت | أوامر الصيانة والنسخ الاحتياطي وإعادة التحميل |

قواعد الحماية:

- لا يمكن استهداف مالك السيرفر أو البوت أو عضو برتبة أعلى أو مساوية.
- الرتب المُدارة أو المتكاملة لا تُعدّل.

- كل قاعدة Automod: إيجابية وسلبية، مع استبعادات.

- السحوبات: إغلاق في الوقت، إعادة سحب، عضو غادر، متطلبات.
- التذاكر: فتح، استلام، إضافة، إغلاق، نسخة، تقييم، حد أقصى.
- الموسيقى: قائمة، تخطي، مغادرة القناة، انقطاع العقدة.
- الجدول: إعادة تشغيل، مهمة مكررة، فشل ثم إعادة محاولة.

- اللوحة: دخول، CSRF، RBAC، XSS، حد معدل.
- فحص إيموجي: كل i18n وبيانات الأوامر.
- استعادة نسخة: إنشاء، تعديل، استعادة، تحقق.

### 11.3 بوابات الجودة

- `npm run check` = `typecheck` + `lint` + `test` + `emoji:check` + `i18n:check`.
- تغطية لا تقل عن 80% للنواة والخدمات، ولا تُحتسب ملفات العرض.
- لا دمج دون CI أخضر.
- لا تسليم وحدة دون: أوامر، i18n، صلاحيات، اختبارات، تدقيق، مفتاح تعطيل، توثيق.
- مراجعة أمنية قبل المرحلة النهائية.
- `npm audit` بلا ثغرات عالية أو متوسطة غير مبررة.
- اختبار استعادة نسخة قبل الإطلاق.

## 12. التشغيل والنشر

### 12.1 التثبيت المحلي على Windows

الجهاز لا يحتوي Node أو Git أو Docker. الخطوات الأولى:

1. تثبيت Node.js 22 LTS وGit عبر winget.
2. التحقق من الإصدارات.
3. إنشاء المشروع وتثبيت الاعتماديات.
4. إنشاء تطبيق ديسكورد وتفعيل الـ intents المطلوبة.
5. تشغيل `npm run setup` لإدخال التوكن و`CLIENT_ID` و`GUILD_ID` و`OWNER_ID`.
6. تشغيل الترحيلات وتسجيل الأوامر.
7. تشغيل `npm run doctor`.
8. تشغيل البوت.

### 12.2 الإعداد

- `.env` فقط للأسرار، و`.env.example` موثّق.
- تحقق Zod عند الإقلاع، وفشل سريع عند نقص إعداد.
- `GUILD_ID` إلزامي، ورفض العمل في سيرفر آخر.
- `OWNER_ID` إلزامي لأوامر الصيانة.
- إعدادات Lavalink اختيارية.

### 12.3 التشغيل

- تطوير: `npm run dev`.
- بناء: `npm run build`.
- تشغيل: `npm start`.
- فحص: `npm run check`.
- نسخ احتياطي: `npm run backup`.
- استعادة: `npm run restore -- <file>`.
- خدمة Windows عبر NSSM اختياري، أو Task Scheduler.
- Linux عبر systemd أو Docker Compose.

### 12.4 النسخ الاحتياطي

- حزمة يومية تضم SQLite (عبر `VACUUM INTO` أو `backup` API) ومجلد نسخ التذاكر وModmail والملفات المرجعية في قاعدة البيانات.
- الاحتفاظ 14 يومًا افتراضيًا.
- نسخة قبل كل ترحيل.
- ملفات النسخ في `backups/` خارج git.
- سكربت تحقق يفتح النسخة ويشغّل استعلامات سلامة، ويتأكد من وجود الملفات المشار إليها.
- نسخة خارج الجهاز اختيارية عبر `BACKUP_COPY_TO` (قرص خارجي أو مسار شبكة)، مع تشفير اختياري.
- اختبار استعادة دوري موثّق يتحقق من قاعدة البيانات والملفات معًا.

### 12.5 المراقبة

- سجلات Pino يومية مع دوران.
- ويب هوك أخطاء اختياري.
- `/health` محلي.
- `/stats` و`/doctor`.
- سجل تدقيق لكل عملية حساسة.
- تنبيه عند فشل مهمة مجدولة متكرر.

### 12.6 التحديث والتراجع

- `git pull` ثم `npm ci` ثم ترحيل ثم إعادة تشغيل.
- نسخة قبل الترحيل.
- التراجع = استعادة النسخة + الرجوع إلى الإصدار السابق.
- لا ترحيل تلقائي في الإنتاج دون نسخة.
